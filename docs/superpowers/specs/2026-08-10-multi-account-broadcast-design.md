# 多账户轮流群发（多开）设计

日期：2026-08-10
状态：设计待 review

## 1. 背景与目标

wxassistant v1.0.2 目前只支持**单微信窗口**：`find_window()` 枚举时取第一个匹配窗口，所有操作绑定 `self._hwnd`。多开时工具永远连错窗口。

客户需求：**同时登录多个微信账号，一份群发任务自动在多个账号窗口之间轮流完成，提升发送效率**（分摊单账号发送量，降低风控风险）。预计最多 4-5 开。

### 核心目标
1. 客户点击一次 [多开]，引导绑定所有微信窗口到账户
2. 点一次 [开始发送]，自动在多个账户窗口间轮流群发各自的名单
3. **OCR 验证并行化** —— 这是单窗口流程的耗时大头（约 1s/人），多开时挪到后台并行
4. 保持单账户模式完全不变（兼容现有使用）

### 关键决策（已与用户确认）
| # | 决策 | 结论 |
|---|------|------|
| 1 | 多开触发方式 | **不自动检测**。用户手动点 [多开] 按钮才进入多开模式，打开多开界面后关闭主界面进入引导 |
| 2 | 多开配置持久性 | **每次手动进多开**。多开绑定只在当次会话内有效，退出即弃；每次都要重新引导 |
| 3 | 名单与账户关系 | 每账户各自名单（从该账户扫描/导入），发送时切到该账户窗口发它的名单 |
| 4 | 账户识别方式 | 前台确认法（逐个激活窗口→用户确认账户名），零 OCR、零坐标依赖 |
| 5 | "同时发"的含义 | 非真并行，**流水线交错**：前台操作串行（全局前台锁），OCR 计算后台并行 |
| 6 | 校准/坐标分账户 | 全局一套 + 每账户覆盖（新增账户继承全局，改一个值自动变专属） |
| 7 | 窗口布局 | 平铺，发送前检测重叠（有重叠提示继续/取消） |
| 8 | 搜索弹窗延迟 | 几乎不延迟 → 前台段内 Enter 后立即检测并关闭 |

## 2. 架构总览

```
单账户模式（默认）：现有代码路径，完全不变
      │  点 [多开]
      ▼
多开引导（独立窗口）：枚举窗口 → 逐个确认账户名 → 会话级绑定
      │
      ▼
多账户模式：1 个全局前台锁 + N 条账户工作线程
   账户1线程 ─► [搜索段(前台)] ─► [OCR后台] ─► [发送段(前台)] ─► 下一人
   账户2线程 ─► [搜索段(前台)] ─► [OCR后台] ─► [发送段(前台)] ─► 下一人
                  ▲ 全局前台锁：同一时刻仅一个线程能进入前台段
```

**为什么不是真并行**：Windows 同一时刻只有一个前台窗口。SetForegroundWindow 和系统剪贴板都不允许跨窗口并行。真正的并行点只有 OCR 计算（CPU 密集，与另一窗口的前台操作重叠）。

**效率来源**：单窗口时每次 OCR（~1s）期间前台空转；N 开时这段空闲被其他窗口的前台段填满，吞吐接近 N 倍（受激活开销和前台段长度制约）。

## 3. 账户绑定（[多开] 引导）

### 触发
- 通讯录列表上方新增 **[多开]** 按钮
- 点击 → 关闭工具主界面 → 打开多开引导窗口
- 引导完成 → 工具以多账户模式界面运行

### 引导流程
```
1. EnumWindows 收集所有匹配微信窗口（复用 find_window 的匹配逻辑，改为返回全部）
   - 窗口数量 0 → 提示"未找到微信窗口，请先登录微信"
   - 窗口数量 1 → 提示"当前仅检测到 1 个微信窗口，多开需要先登录多个账号"（可继续或取消）
2. 对每个窗口（按枚举顺序）：
   a. SetForegroundWindow 激活到最前（复用 activate_window，校验 GetForegroundWindow==目标，失败重试）
   b. 弹确认框：「这个窗口是你的哪个账户？」
      选项：新账户名输入框（默认 账户1/账户2…）+ 跳过该窗口
   c. 记录 {窗口hwnd, 账户名, 顺序}
3. 全部确认后展示绑定列表（账户名 ↔ 窗口顺序），允许改名字/删除
4. 确定 → 生成会话级账户列表，进入多账户模式
```

### 绑定数据（会话级，不落盘跨会话）
绑定信息保存在内存中。可选：写 `cache/multiopen_session.json` 供崩溃恢复提示，但**不作为下次启动的依据**（决策 #2）。

## 4. 数据模型

### 会话内结构
```python
@dataclass
class MultiAccount:
    accounts: list[AccountWindow]   # 绑定顺序 = 发送顺序
    # 每个账户独立状态机在各自线程内

@dataclass
class AccountWindow:
    name: str          # 用户确认的账户名（如 "账户1"）
    hwnd: int          # 本会话的窗口句柄
    order: int         # 绑定顺序
    friend_list: list  # 该账户勾选的好友（来自 FriendService）
```

### 每账户好友名单（持久化）
```
cache/friends.json              # 单账户模式 / 全局默认（现有文件，兼容）
cache/friends_{account_name}.json  # 多开时每账户一份
```
账户名做文件名规范化（非法字符替换）。FriendService 增加 `account` 参数，为 None 时读写全局文件。

### 坐标/OCR 校准（全局一套 + 每账户覆盖）
```
cache/coordinates.json          # 全局默认（现有）
cache/ocr_calibration.json      # 全局默认（现有）
cache/coordinates_{name}.json   # 仅该账户单独设置过时才存在
cache/ocr_calibration_{name}.json
```
- **读取**：按 账户专属 → 全局 逐级回退
- **新增账户**：不复制文件，读取时回退到全局（继承）
- **写入**：在"当前选中账户"上下文里改一个值 → 生成该账户专属文件
- **心智模型**：校准/坐标永远属于"当前选中的账户"

## 5. UI 改动

### 主界面（多账户模式）
- 左侧新增**账户选择器**（下拉，顶部）：切换时加载该账户名单 + 坐标/校准上下文
- 通讯录列表上方 **[多开]** 按钮（单账户模式也显示）
- 发送按钮语义：多账户模式下为**对全部已绑定账户轮流发送各自的已勾选名单**
- 进度区按账户分段显示；结果弹窗按账户分组

### 设置对话框
- **设置→多开**（新页）：所有时序延迟参数（见 §7）
- **设置→坐标 / 设置→OCR**：页顶部加账户下拉 `[全局默认 / 账户1 / 账户2 …]`
  - 未单独设置的账户显示灰字"继承全局"
  - 修改一个值 → 自动写入该账户专属文件
- 校准工具（calibrate_ocr）运行时绑定当前选中账户

## 6. 发送编排（流水线）

### 全局前台锁
```python
foreground_lock = threading.Lock()
```
同一时刻仅一个线程持有，进入前台段前获取，段结束释放。锁内禁止长等待。

### 账户线程主循环（每账户一条）
```
对每个已勾选好友：
  ① 前台段A：抢锁 → 激活窗口(GetForegroundWindow已是本窗口则跳过)
              → Ctrl+F → 粘贴名 → Enter
              → 弹窗检测(立即；有弹窗=无此人→标记失败，跳过) 
              → 截图(chat_title 区域，用该账户校准) → 放锁
  ② 后台：RapidOCR 识别截图 → 归一化 → 四层匹配（复用 match_chat_title 逻辑）
  ③ 前台段B：抢锁 → 验证匹配
              → 匹配：粘贴模板+Enter 发送 → 记录成功
                → 顺手搜索下一个好友 + 弹窗检测 + 截图（合并操作减少抢锁）
              → 不匹配：记录失败 → 放锁
```

### 调度约束
- **前台段内尽量合并操作**（发送+下一个搜索+截图），每好友平均 1.5 次前台段
- 前台段内禁止 OCR（OCR 必须放后台，否则流水线退化成顺序）
- 激活跳过优化：若目标窗口已在最前，跳过 SetForegroundWindow（省 0.2s×N）

### 发送前重叠检测
```
枚举所有账户窗口 GetWindowRect → 两两计算交叠面积
有重叠 → 弹窗「检测到窗口重叠，可能互相遮挡导致发送错误」[继续 / 取消]
引导时也提示"请将微信窗口平铺、勿重叠"
```

### 中断
- 用户按中断 → 设置全局停止标志 → **N 个线程**都退出循环
- 每个线程退出前清理现场：关闭自己窗口残留弹窗、恢复钩子状态
- 等待所有线程 join 后恢复 UI，展示已完成部分的结果

## 7. 设置→多开（延迟参数）

| 参数 | 默认 | 说明 |
|------|------|------|
| 激活延迟 | 0.2s | SetForegroundWindow 后等待 |
| 搜索后延迟 | 0.1s | Enter 后、弹窗检测前 |
| 就绪检测超时 | 2.0s | 切回后等待窗口就绪，超时重试一次 |
| 账户切换间隔 | 3.0s | 两个账户最后一步之间（防风控） |
| 发送间隔 | 0.1s | 复用现有 INTERVAL_JITTER_RATIO ±30% |
| 弹窗检测重试次数 | 0 | 弹窗几乎不延迟，默认不重试 |

所有参数走现有 `cache/settings.json` 扩展，带 `multi_open_` 前缀。

## 8. 风险与对策

| # | 风险 | 对策 |
|---|------|------|
| 1 | **搜索弹窗归属错误**：A 窗口弹"添加朋友"残留屏幕，B 窗口把它当自己的关掉 → 切回 A 无弹窗无结果 → OCR 匹配到旧聊天 → **误发** | 弹窗只用 **PID 判定**（与发出搜索的窗口同进程）；弹窗检测+关闭锁在发出搜索的窗口自己的前台段内，切走前现场干净 |
| 2 | 剪贴板竞争：两窗口并发 pyperclip.copy 互踩 | 复制→粘贴→Enter 保持连续，锁在前台段内不跨段 |
| 3 | 截图串窗口/截到遮挡 | 禁止对后台或被遮挡窗口截图；截图在自己前台段内抓取 |
| 4 | 切回时窗口未就绪（加载中） | 就绪检测（等待标题/搜索框稳定），OCR 无效重试一次 |
| 5 | 中断钩子 `_hook_suspended` 全局布尔被两线程交错 suspend/resume 错乱 | 改**引用计数**，或每线程跟踪自己的段 |
| 6 | SetForegroundWindow 被 Windows 前台锁定拒绝 → 键盘落到错误窗口 → **发错人** | 每次激活后校验 GetForegroundWindow==目标，失败重试；失败不继续 |
| 7 | 窗口重叠遮挡 | 发送前重叠检测 + 引导提示平铺 |
| 8 | 风控：N 开使全局发送频率 ×N | 账户切换间隔可调；保持每账户发送间隔防抖 |
| 9 | 窗口大小不同 → 百分比坐标错位 | 每账户覆盖校准（§4） |
| 10 | 结果汇总复杂化（N 个账户） | 按账户分组展示，复用现有 ResultDialog 结构扩展 |

## 9. 兼容性

- **单账户模式完全不变**：`find_window()` 原逻辑保留，多开只是新增了"返回全部窗口"的重载；`self._hwnd` 语义在单账户下不变
- 多账户模式下 `self._hwnd` 由每线程持有的账户窗口替代，原 bridge 方法签名尽量不动（新增参数或新方法，避免破坏单账户路径）
- 现有 `cache/*.json` 文件格式不动，仅新增每账户覆盖文件
- 不做自动迁移；首次多开引导时自动识别现有好友名单归属全局默认

## 11. 测试策略

- **引导**：无窗口/1 窗口/2+ 窗口；窗口顺序变化；取消/跳过
- **弹窗归属**：A 弹窗残留时切 B，B 不得误关/误判（重点回归，可手动构造）
- **流水线**：2 账户各 5 人，验证交错顺序、OCR 并行不阻塞、无跨窗口误发
- **中断**：发送中按中断，两个线程都停、无残留弹窗
- **重叠**：叠放窗口被拦截提示；平铺通过
- **校准**：全局继承 → 改一值变专属 → 另一账户不受影响
- **压测**：5 开各 20 人，监控每账户完成时间和总体吞吐
